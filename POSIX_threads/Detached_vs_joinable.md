При выполнении работы, посвященной созданию detached потоков в цикле, порой встречается поведение, которое мы как будто не ожидаем увидеть. 
Ожидаем, что потоки будут создаваться, выполнять поточную функцию, завершаться, и их ID будут переиспользоваться. Однако так происходит далеко не всегда. 

Всякий раз, когда мы сталкиваемся с непонятным поведением нашего кода, следует вспоминать, что Linux является логичной системой, в которой нет "подземного стука", а все проблемы могут быть вызваны всего несколькими причинами.
Разберем причины, по которым такая программа может завершиться с ошибкой "Resource temporary unavailable". Очевидно, что причиной является достижение какого-то лимита, но какого же именно?

Давайте разбираться, что происходит.

### Как потоки выглядят для ядра

Для ядра Linux нет никакой разницы между joinable и detached потоками. Любой поток создается через системный вызов clone() и увеличивает счетчик Tasks (задач).
Разница между ними исключительно «косметическая» и живет на уровне библиотеки pthread.
* У joinable потока структура данных (pthread_t) и его стек остаются в памяти после завершения работы потока и ждут, пока main вызовет pthread_join (чтобы забрать код возврата и освободить ресурсы).
* У detached потока ресурсы очищаются автоматически в момент его завершения.
Но пока поток запущен и работает, он занимает полноценное место в таблице процессов ядра.

Посмотреть, сколько потоков запущено в рамках работающей программы, можно через файловую систему /proc, где потоки каждого процесса видны в директории /proc/PID/task/, а вы можете легко сосчитать их количество.
Например, листинг такой директории может выглядеть так:
```
/proc/201209/task/:
201209  201213  201215  201224  201226  201229  201231  201247  201249
201212  201214  201216  201225  201228  201230  201232  201248
```
### В какие лимиты упирается лавина потоков?

Лимиты от глобальных к локальным

| Лимит | Где настраивается (как посмотреть) | На что влияет |
| ----- |---------------------------------- | ------------- |
| ```pid_max``` | /proc/sys/kernel/pid_max | Глобальный системный лимит на сумму всех PID/потоков в OS. Обычно равен 32768 или 4194304. Если он исчерпан, сервер «ложится» целиком.|
|```max_user_processes```|ulimit -u или /etc/security/limits.conf|Лимит на суммарное число задач (процессов + потоков) для конкретного UID.|
|```TasksMax```|systemd (user-UID.slice)|Ограничение cgroups на все процессы пользователя суммарно по всем сессиям. В современных Linux именно он срабатывает первым.|

###  Механика падения. Почему EAGAIN?

Когда в цикле вызывается pthread_create(), происходит следующее:
1. Библиотека выделяет память под стек нового потока.
2. Происходит системный вызов clone().
3. Ядро Linux берет этот вызов и идет проверять контрольные группы (cgroups) текущего слайса пользователя: «Превышен ли параметр TasksMax?»
4. Если лимит превышен, ядро говорит: «Стоп, больше создавать задачи этому пользователю нельзя» и возвращает из системного вызова код ошибки EAGAIN.
5. Функция pthread_create() перехватывает этот код и возвращает его программе.
6. В C через strerror(errno) эта ошибка превращается в строку "Resource temporarily unavailable".

### Почему detached статус не спасает?

Расчет на то, detached потоки будут быстро исчезать, однако, скорость генерации новых потоков (clone()) на несколько порядков выше, чем скорость завершения. 
В итоге TaskMax заполняется, ядро выдает EAGAIN и программа завершается. 

### Почему не Out of Memory или Killed (при содействии out of memory killer)?

Как же именно ядро "обманывает" программу ради оптимизации производительности?

1. Когда pthread_create запрашивает стек (допустим, те самые 8 МБ по умолчанию), библиотека делает системный вызов mmap. Ядро Linux одобряет этот запрос, выделяет виртуальное адресное пространство, но не выделяет ни одного байта реальной физической памяти (RAM). Для системы эта память пока бесплатна.
2. Как отрабатыавют Copy-on-Write (COW) и Lazy Allocation. Физическая память выделяется страницами (обычно по 4 КБ) и только тогда, когда поток начинает реально писать данные в стек (например, создавать локальные переменные или вызывать новые функции). Ядро ловит исключение Page Fault (страничный сбой), незаметно выделяет физическую страничку 4 КБ и возвращает поток к работе.
3. Почему лимит памяти не играл роли в этой части лабораторной работы?  В рекурсивном цикле потоки плодились мгновенно, но внутри себя они почти ничего не делали — printf() довольно легкая операция. Каждый поток успевал «загрязнить» в RAM от силы одну-две странички (около 4–8 КБ) физической памяти, хотя виртуально занимал 8 МБ.
В итоге, чтобы упереться в лимит оперативной памяти сервера (допустим, 16 ГБ RAM), программе потребовались бы миллионы активных потоков. Но жесткий лимит TasksMax в systemd (который обычно исчисляется тысячами) сработал как молниеносный предохранитель. Он заблокировал создание новых задач (EAGAIN) в тот момент, когда физическая RAM сервера была практически нетронутой.
Это потрясающий пример того, как в Linux концепция виртуальной памяти и механизмы cgroups работают, защищая систему от падения.

Упражнение: Посчитайте, сколько оперативной памяти требуется для того, чтобы честно и сразу выделить память на весь лимит потоков.

### Как изменить лимиты

#### pid_max
Временно, до первой перезагрузки:
```
echo 65536 > /proc/sys/kernel/pid_max
```
Или
```
sysctl -w kernel.pid_max=65536
```
Постоянно:

Поскольку /proc генерируется ядром в оперативной памяти, после перезагрузки все изменения сотрутся. Чтобы зафиксировать новое значение навсегда, его нужно прописать в конфигурационный файл на диске — /etc/sysctl.conf (или в отдельный файл внутри /etc/sysctl.d/):

```
kernel.pid_max = 65536
```
#### TaskMax

* Для конкретного пользователя навсегда
```
 sudo systemctl set-property user-UID.slice TasksMax=NEW_TASKS_LIMIT
```
Вместо UID нужно подставить id пользователя, а вместо NEW_TASKS_LIMIT - новое число. Совсем убрать лимит можно подставив TasksMax=infinity. Не ставьте слишком маленькое число, иначе придется перезагружать систему в однопользовательском режиме и менять лимиты на нормальные в этом режиме. 

* Для конкретного пользователя временно
```
 sudo systemctl set-property --runtime user-UID.slice TasksMax=NEW_TASKS_LIMIT
```
* Глобально для всех
  
По умолчанию в современных дистрибутивах (например, в Ubuntu 24.04) для пользовательских слайсов установлен лимит, который часто равен 33% от общего системного максимума (обычно это около 10 000–30 000 задач).
Посмотреть общесистемный лимит можно следующей командой
```
systemctl show --property DefaultTasksMax
```

Чтобы изменить этот стандарт для всех:
1. Откройте файл глобальных настроек: /etc/systemd/logind.conf
2. Найдите (или раскомментируйте) строку: UserTasksMax=
3. Задайте нужное значение (например, UserTasksMax=40000 или infinity).
4. Перезапустите службу, чтобы применить настройки: ```systemctl restart systemd-logind```

* Как проверить для текущего пользователя
  ```
  systemctl status user-`id -u`.slice | grep Tasks
  ```
